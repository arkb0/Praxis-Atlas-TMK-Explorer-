Dynamic programming (DP) is a method for solving optimization and counting problems by breaking them into overlapping simpler subproblems, solving each subproblem once, and combining those solutions to form an optimal solution to the original problem.

Key ideas:
- Optimal substructure: An optimal solution to the problem can be constructed from optimal solutions to its subproblems.
- Overlapping subproblems: Subproblems recur many times; solving each once and storing the result avoids recomputation (memoization or tabulation).
- Recurrence: You identify subproblems and write a recurrence that expresses the value of a subproblem in terms of smaller subproblems.
- DP table: You fill a table (1D, 2D, or higher) in a specific order that respects dependencies, usually from smallest subproblems to larger ones.
- Reconstruction: If needed, you store choice information (prev pointers) to reconstruct an optimal solution path.

How it works in practice (high-level steps):
1) model the problem as a set of subproblems: decide what parameters uniquely identify a subproblem (e.g., indices i, j, remaining capacity, etc.).
2) derive a recurrence: express the solution for a subproblem in terms of solutions to smaller subproblems.
3) initialize base cases: set the known values for the simplest subproblems.
4) determine an order to fill subproblems: typically increasing in size or along a topological order, to ensure all dependencies are computed before they’re used.
5) fill the table: compute and store values (and often back-pointers to recover the actual solution).
6) extract the answer: read off the final subproblem’s value (and reconstruct the full solution if needed).
7) analyze complexity: determine time and space by counting subproblems and work per subproblem.

Common DP patterns you’ll see:
- Longest Increasing Subsequence (LIS): subproblems based on prefixes or index pairs; O(n^2) time, O(n) or O(n^2) space.
- Longest Common Subsequence / Edit Distance: subproblems with two indices (i, j) over two strings; O(nm) time, O(nm) space.
- Knapsack (0/1 or unbounded): subproblems by item and capacity; O(nW) time, O(W) or O(nW) space.
- Matrix Chain Multiplication: subproblems by interval [i, j]; O(n^3) time, O(n^2) space.
- Floyd-Warshall / Bellman-Ford: graph-based DP with subproblems defined over pairs of nodes or node sets; O(n^3) time for Floyd-Warshall, etc.
- DAG shortest paths: DP over a topologically sorted DAG; linear in number of edges plus vertices.
- LCS with path reconstruction: use a table for lengths and a separate structure to recover the sequence.

Nice question. This is a classic DP tiling/counting problem with three tile shapes that advance coordinates by different steps from a starting cell.

Problem restatement in DP terms:
- We want the number of ways to fill a n x n grid from (1,1) to (n,n) using three “tiles” (letters) that extend the filled region as follows:
  - Tall letter: from (i,j) to (i+3, j+2)
  - Wide letter: from (i,j) to (i+1, j+2)
  - Squarish letter: from (i,j) to (i+1, j+1)
- We assume tiles can be placed when their entire footprint stays within the target square, and placements do not overlap (standard tiling interpretation).
- We want the number of tilings of the n x n square starting at (1,1) ending exactly at (n,n) with these moves in a DP-feasible formulation.

DP modeling approach (one valid formulation):
- Subproblem: Let DP[i][j] be the number of ways to fill the sub-rectangle from (1,1) to (i,j) completely, i.e., to end exactly at (i,j).
- Base case: DP[0][0] = 1 if you like 0-indexing; otherwise DP[1][1] = 1 as the starting cell is considered already filled.
- Transitions: To end at (i,j), you must place one of the three tiles so that its footprint ends at (i,j) and its footprint lies within the grid:
  - Tall tile ends at (i,j) if it started at (i-3, j-2). This tile covers a region that reaches to (i, j) from (i-3, j-2). Contribution: DP[i-3][j-2], valid when i-3 >= 1 and j-2 >= 1.
  - Wide tile ends at (i,j) if started at (i-1, j-2). Contribution: DP[i-1][j-2], valid when i-1 >= 1 and j-2 >= 1.
  - Squarish tile ends at (i,j) if started at (i-1, j-1). Contribution: DP[i-1][j-1], valid when i-1 >= 1 and j-1 >= 1.
- Recurrence (for i,j within [1..n]):
  DP[i][j] = (i-3 >= 1 && j-2 >= 1 ? DP[i-3][j-2] : 0)
           + (i-1 >= 1 && j-2 >= 1 ? DP[i-1][j-2] : 0)
           + (i-1 >= 1 && j-1 >= 1 ? DP[i-1][j-1] : 0)

- Answer: DP[n][n].

Notes on indexing and edge handling:
- If you prefer 0-based indexing, adjust indices accordingly:
  DP[x][y] counts ways to fill sub-rectangle up to (x,y) (inclusive), with transitions:
  DP[x][y] = (x-3>=0 && y-2>=0 ? DP[x-3][y-2] : 0)
           + (x-1>=0 && y-2>=0 ? DP[x-1][y-2] : 0)
           + (x-1>=0 && y-1>=0 ? DP[x-1][y-1] : 0)
  Base: DP[0][0] = 1; DP[others with any negative index] treated as 0.
- Fill order: row-major or any topological order that ensures all RHS indices are computed before DP[i][j]. A straightforward loop: for i from 1 to n, for j from 1 to n, compute DP[i][j] using the three terms. If you use 0-based indices, loop x from 0..n-1 and y from 0..n-1.

Complexity:
- Time: O(n^2) states, each with O(1) work, so O(n^2).
- Space: O(n^2) for DP table (you can optimize to two or three diagonals if memory is a concern, but here a full table is simplest).

In a reduction proof, the direction of the reduction must go from the known hard problem A to the target problem B: A reduces to B (A ≤p B). This means you show how any instance of the known NP-hard problem A can be transformed in polynomial time into an instance of B such that:

- If the original instance of A has a solution, then the transformed instance of B has a solution.
- If the original instance of A has no solution, then the transformed instance of B has no solution.

Why this direction? Because it preserves hardness: solving B would give a solution to A via the polynomial-time back-mapping (the reverse mapping). If you tried the opposite direction (reducing B to A), you wouldn’t establish that B is at least as hard as A; you’d be showing how to solve A using B, which doesn’t prove B is NP-hard.

Key points:
- The forward direction is A → B (A reduces to B).
- The reduction must be computable in polynomial time.
- You also provide a polynomial-time decoding/back-mapping from B-solutions to A-solutions to complete the reduction.
